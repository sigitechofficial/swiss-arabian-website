# Swiss Arabian storefront — performance & SEO baseline (2026-11-13)

Reference point for the multi-brand work: every brand site (Swiss Arabian after the brand-pack refactor, Sapil, later brands) is compared against these numbers.

## How it was measured

| Item | Value |
|------|-------|
| Build | `next build` (Next.js 16.3.2, Turbopack), branch `feat/homepage-start-from-storefront`, `next start` on :3004 |
| Data | Local backend (:3002), catalog images from Azure dev blob storage |
| Tool | Lighthouse 12.8.2, mobile preset (simulated slow 4G, 4× CPU slowdown), 3 runs per page, **median** reported |
| Pages | `/`, `/products`, `/collections/flash-sale`, `/products/zahra-candy` |
| Not included | Real-user data (CrUX), production CDN, GTM / GA4 (not set locally). Insider **is** loaded |

SEO score is pulled down by `is-crawlable` because indexing is off locally (`noindex`, `robots: Disallow /`). That part is expected and not a defect.

## Findings, ranked by impact

1. **Images are the biggest cost.** Home ships 7.2 MB of images. Lighthouse estimates 5.0 MB savings from correct sizing and 3.5 MB from AVIF/WebP. Several home and collection images are plain `<img>` pointing at blob storage, bypassing Next's image optimiser.
2. **Heavy React work on the main thread.** On `/products` the framework chunk (`react-dom`, 233 KB) accounts for about 14.5 s of script time under 4× CPU slowdown (TBT ≈ 1 s). Home and product page: 2–2.8 s. This points to an expensive render or hydration, or repeated re-renders, on the product grid (about 1,000 DOM nodes). Profile it with the React Profiler.
3. **The LCP image is lazy-loaded** on `/products` (`lcp-lazy-loaded`). The first product image should be eager with high priority. The product page and collection LCP images are also late (`lcp-discovery`).
4. **Every route is dynamic.** The root layout calls `headers()` (`src/app/layout.tsx`), so no page is pre-rendered or cached. TTFB is 0.2–0.9 s locally and will be worse under load. Fixing the brand per deployment lets catalog pages use static rendering or ISR.
5. **Unused JavaScript:** 116–181 KB per page. There is also 13 KB of legacy polyfills.
6. **No meta description** on `/products` and on collection pages.
7. **Console errors on every page:** 404, 400 and 422 API responses.
8. **Accessibility issues to fix:** `aria-valid-attr-value`, `label-content-name-mismatch`, `target-size`, `link-name` / `link-text`, `image-redundant-alt`.
9. **Third party:** Insider costs 110 KB and about 350 ms of main thread on every page. GTM and GA4 aren't measured yet and will add to this.
10. **Back/forward cache** is not used (`bf-cache` fails).
11. **Global CSS** is 372 KB raw and render-blocking (Tailwind output plus `flag-icons` imported in `globals.css`).

## Already good

- CLS is 0.00 on all pages.
- FCP is about 1.7 s.
- SEO markup: one H1 per page; canonical and hreflang (en/ar/x-default) built from the request host; Open Graph tags; JSON-LD (Organization, WebSite, Product, ItemList, BreadcrumbList); correct `lang` and `dir` on Arabic pages.
- The sitemap is generated from the request host (681 URLs), which is what multi-brand needs.

## After fix 1: images and LCP loading (same day, same method)

Changes: product cards, home rails, the hero, collection tiles, CMS banners and the collection banner now go through the Next image optimiser with correct `sizes`. The first grid row loads eagerly, and the first card gets `fetchPriority="high"`. Hover ("ingredients") images are fetched card-sized, only after the page is idle, and only on hover-capable screens. The full-size preloads of every hover image and hero slide were removed.

| Page | Perf | LCP | TBT | Total weight | Images |
|------|-----:|----:|----:|-----:|-----:|
| Home | 64 → 61 | 5.8 → 5.4 s | 551 → 724 ms | 8.1 MB → **2.4 MB** | 7.2 MB → **1.5 MB** |
| Product list | 52 → **64** | 7.3 → 6.4 s | 998 → **490 ms** | 3.4 MB → **1.0 MB** | 2.5 MB → **0.12 MB** |
| Collection | 59 → 63 | 6.0 → 6.0 s | 744 → 572 ms | 4.6 MB → **1.0 MB** | 3.7 MB → **0.13 MB** |
| Product page | 54 → 60 | 5.7 → 5.9 s | 1,152 → 691 ms | 1.5 → 1.2 MB | 544 → 203 KB |

Page weight is down 22–78%, and images are down 63–97%. LCP barely moved: the LCP image now downloads in under 0.1 s, but it is **discovered late** (load delay of about 1.4–3 s, because cards render only after the JavaScript runs) and **painted late** (render delay of 2–4 s, because the main thread is busy). The next fixes are therefore JavaScript and server rendering, not images.

Collection accessibility went from 92 to 88 because an "Out of stock" chip (white text on `#8a8178`, contrast 3.8:1) is now in the first row. That comes from stock data, not this change, and is a styling fix for the accessibility pass.

## After all fixes (same day, same method)

Additional fixes:
- **Endless re-render loop** in `WishlistStatusScope` / `WishlistHeartButton`. It ran about every 5 ms on every product grid for as long as the page was open; the product list went from about 1,200 re-renders to 14.
- **Market-aware requests:** the cart, home notes and video requests now wait for the market; the cart drawer's rail loads only when the drawer opens.
- **Meta descriptions** for product listings.
- **Flag CSS** loads only with the phone field.
- **Accessibility fixes.**

|------|-----:|----:|----:|----:|----:|----:|
| Home | 64 → 61 → **68** | 5.8 → 5.4 s | 551 → **404 ms** | 4.7 → 2.6 s | 92 → **100** | 96 → **100** |

| Collection | 59 → 63 → 61 | 6.0 → 6.1 s | 744 → 604 ms | **15.0 → 2.8 s** | 92 → **100** | 96 → **100** |

SEO audits: the only remaining failure is `is-crawlable`, which is the expected local `noindex`. The home "Read more" link text was fixed after this run.

Console errors: none, except the product page's `you-may-also-like` 404. That collection is not set up in this market, which is data, not a bug.

**Still over budget:** LCP (5.4–6.5 s) and TBT (400–600 ms). The LCP image is now discovered late (1.3–3.3 s load delay, because the product grid renders on the client) and painted late (2.4–4 s render delay, from hydration). What remains:
- server-rendered, static catalog pages (needs the root layout to stop reading request headers; planned with the per-brand deployment and `[locale]` routing)
- a smaller hydration cost
- Insider timing (a marketing decision)

## Re-running

Raw Lighthouse JSON for this run was kept outside the repo. To reproduce: build, run `npm start`, then for each page run
`npx lighthouse@12 http://localhost:3004<path> --only-categories=performance,seo,accessibility,best-practices --output=json` three times and take the median.
